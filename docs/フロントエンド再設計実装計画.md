# フロントエンド再設計 実装計画 — MangaVault リニューアル

> 対象: `frontend/` を破棄に近い形で作り直す。
> 基準ドキュメント: [`docs/design/DESIGN_SPEC.md`](design/DESIGN_SPEC.md) ＋ `docs/design/漫画下载管理.dc.html` ＋ `docs/design/screenshots/`
> バックエンド（FastAPI / API・データモデル）は**変更しない**。

---

## 0. 大前提（ユーザー指定の制約）

1. **デザイン稿の再現を最優先**する。`docs/design` のUIをそのまま再現することがゴール。
   **そのUIでは実現できない既存機能がある場合に限り**、最小限のUIを追加する。
2. フロントは **Next.js をやめ、React + Tailwind CSS で再構築**する。
   （ビルド基盤は Vite を採用＝ React SPA）
3. **旧フロントの挙動を厳密に再現する必要はない。新UI（デザイン稿）を優先**する。
   React + Tailwind でより素直に書ける代替があればそれを使う。旧コードの移植は「楽だから使う」程度の位置づけで、UI都合で書き直してよい。

→ つまり「新UI＝デザイン稿の再現が最優先」。デザイン稿に存在しない装飾・機能は原則足さない。
追加が許されるのは §4 で挙げる *UIに居場所が無い既存機能* と、§4.4 のカード更新日時のみ。

## 1. 技術スタックの移行（Next.js → React + Tailwind）

### 1.1 採用構成
| 項目 | 旧（破棄） | 新 |
|---|---|---|
| フレームワーク | Next.js 16 (app router) | **React 19 + Vite (SPA)** |
| スタイル | Tailwind v4 + 大量の shadcn/ui | **Tailwind + CSS変数トークン**（稿§1を正）。UIは原則ハンドメイド |
| テーマ | `next-themes` | **自前 ThemeProvider**（`<html>` に `data-theme` 付与し CSS変数差替、稿§8） |
| 画像 | `next/image` | 素の `<img>`（`loading="lazy"`） |
| ルーティング | app router | 不要（タブは状態管理。必要なら最小限の状態のみ） |
| アイコン | lucide-react | **lucide-react 継続**（フレームワーク非依存） |
| ダイアログ/スイッチ等 | radix 多数 | radix は **Dialog / Switch / Select / DropdownMenu のみ**任意採用（残りは稿に合わせ自作） |

### 1.2 API プロキシ / ベースURL（重要・移行で壊れやすい箇所）
- 現状は Next.js の `rewrites` が `/api/*` → `http://backend:8000` を中継し、フロントは `API_BASE_URL = ""`（同一オリジン）で叩いている。
- Vite SPA では rewrites が無くなるため、**代替が必須**:
  - **開発**: `vite.config.ts` の `server.proxy` で `/api` と `/api/events`(SSE) を `http://localhost:8000` へ。SSE はバッファリング無効・`changeOrigin` 設定。
  - **本番（確定＝案B / §1.3）**: FastAPI が静的ビルドと `/api` を同一プロセス・同一オリジンで提供。これにより `API_BASE_URL = ""` のまま [`lib/api/client.ts`](../frontend-legacy/lib/api/client.ts) をそのまま使える。
- Komga遷移は `window.location.protocol//hostname:25601`（現[`header.tsx`](../frontend-legacy/components/layout/header.tsx)ロジック）を踏襲。

### 1.3 ビルド/デプロイ更新（配信構成＝案B: FastAPI集約・確定）
- **本番は backend(FastAPI) コンテナ1つに集約**。フロントは Vite で `dist/` を生成し、backend イメージに同梱。
  - FastAPI に `StaticFiles` で `dist/` をマウントし、`/api` 以外は `index.html` を返す **SPAフォールバック** を1つ追加。
  - `/api/*` と `/api/events`(SSE) は元々 backend が処理 → 自動的に同一オリジン。`API_BASE_URL=""` 維持。
- **マルチステージ Dockerfile**: ①node で `frontend` をビルド → ②python の backend イメージへ `dist/` をコピー。
  - 旧 `frontend/Dockerfile`（Next standalone）は廃止。
- `docker-compose.yml` / `docker-compose.synology.yml` から **frontend サービスを削除**し、backend がフロントも配信。ポート公開は backend に集約。
- `next.config.mjs` の rewrites は不要（同一プロセスのため）。開発時のみ Vite proxy を使用。

### 1.4 ディレクトリ戦略（確定）
- 既存 `frontend/` は **`frontend-legacy/`（バックアップ）にリネーム**して温存。
- 新しい React + Vite プロジェクトを **`frontend/`** として作成（＝最終的に `frontend` が新フロント）。
- 安定後に `frontend-legacy/` は削除可（当面は参照用に残す）。

## 2. 再利用する資産 vs 作り直す資産

> 制約③より「移植ありき」ではない。**新UIにとって素直なら流用、合わなければ書き直す**。
> 下記は *流用候補* であって必須ではない。

### 2.1 流用候補（フレームワーク非依存・そのまま使える）
- [`lib/api/`](../frontend-legacy/lib/api/) 一式（fetch クライアント／manga・download・sync・tasks・recent-updates・settings）。API契約は不変なので **そのまま使うのが最も楽**。
- [`lib/types/index.ts`](../frontend-legacy/lib/types/index.ts) の型定義。
- SSE 進捗の [`use-task-status.ts`](../frontend-legacy/hooks/use-task-status.ts)（`EventSource` はブラウザ標準）。進捗配線の核なので流用価値が高い。
- feature hooks のロジック（`use-collection` / `use-download` / `use-selection` / `use-delete` / `use-favorite` / `use-recent-updates`）は **参考にしつつ、新UIの状態構造に合わせて再設計**してよい（検索・排序・卡片/列表などの新状態が増えるため）。

### 2.2 作り直す（UIすべて）
- 全 `components/`・`features/**/components/`・`app/` のビュー層。
- shadcn `components/ui/` は原則破棄（稿の厳密値と一致しないため）。必要箇所のみ radix を薄く使う。

## 4. UIに居場所が無い既存機能（=制約①により最小追加が許される項目）

稿を厳密再現すると導線が消える既存機能。**最小限**のUIで補う。

### 4.1 「更新下载状态」（ローカルCBZ走査でDL状態再同期）★追加確定・配置確定
- 既存API: `POST /api/update-download-status`（＋`/verify-files`）。現[`header.tsx`](../frontend-legacy/components/layout/header.tsx)で稼働中。
- 稿のツールバー/設定どちらにも**存在しない**。
- **配置（確定）**: **設定ダイアログ(§6.10) 内に「数据维护／实用工具」セクションを設け、その中の「更新下载状态」ボタン**として置く。
  - 理由: ツールバー(§6.4)の「同步」がオンラインからの主要更新で高頻度。「更新下载状态」はローカルファイル整合用の**低頻度メンテ操作**であり、ツールバーのボタン列を増やすと稿のレイアウトリズムが崩れる。設定内に隔離するのが新UIに最も馴染む。
  - 表示: アクション行＋短い説明文＋実行中スピナー（既存の挙動を踏襲）。結果はトースト(§6.13)で件数表示。

### 4.2 收藏夹カードの「站点收藏(add-to-favorite)」★確定＝最近更新のみ
- 既存API: `POST /api/add-to-favorite`（作者フォルダへ追加）。
- **確定方針**: 站点收藏ハートは **最近更新カード(§6.9) のみ**に置く（同一API）。**收藏夹カードにはハートを追加しない**（稿どおり）。
- これに伴い、收藏夹カードの「DL済・未收藏」黄色インジケータは**廃止**（稿に無い／導線を最近更新へ一本化）。

### 4.3 DL進捗の実値表示 ★追加不要（稿に既存・配線のみ）
- 稿§6.7/6.8 がカード/行にDL中オーバーレイ＋実`%`＋進捗バーを既に定義。
- よって**UI追加ではなく**、稿のオーバーレイに SSE 実データ（`task.manga_id` × `task.progress`）を**配線するだけ**。旧シミュレーション挙動(§8)は実APIに差し替える。

### 4.4 漫画カードの「更新日时」表示 ★追加確定（稿への小修正）
- 稿の漫画カード(§6.7)は更新日时を表示していないが、**表示させたい**（ユーザー指定）。
- データ: `manga.updated_at`（既存）。
- **配置**: カードフッターの作者行付近に、`--text2` の小サイズ(11〜11.5)で日付を1点追加（稿のトーン・余白リズムを崩さない最小修正）。リストビュー(§6.8)・最近更新(§6.9)は元々メタに日付を持つ想定なので整合。

> 上記以外で「旧フロントにあって稿に無い表示」は **追加しない**：
> - カードの `file_size`(MB) 表示 → 稿に無いので**出さない**。
> - 「DL済・未收藏」黄色インジケータ → §4.2 により**廃止**。

## 7. 確定事項 / 残課題

### 確定済み
- 旧挙動の厳密再現は不要・新UI優先（§0-3）。
- 「更新下载状态」= 設定ダイアログ内「数据维护」に配置（§4.1）。
- 站点收藏ハート= 最近更新カードのみ。收藏夹カードはハート無し・黄色インジケータ廃止（§4.2）。
- 漫画カードに更新日时を表示（§4.4）。
- ディレクトリ= 旧 `frontend/`→`frontend-legacy/` 退避、新規を `frontend/`（§1.4）。
- 配信構成= **案B: FastAPI集約**。backend 1コンテナで静的配信＋API、マルチステージビルド、compose の frontend サービス削除（§1.3）。

### 残課題
- なし（全決定済み）。フェーズ0から実装着手可能。
