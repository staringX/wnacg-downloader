## 2. システム方式設計

### 2.1 全体方式

- **アーキテクチャパターン**: SPA（Next.js）+ REST/SSE バックエンド（FastAPI）+ RDB（PostgreSQL）の 3 層 + 閲覧用 Komga。
- **通信方式**:
  - フロント → バックエンド: REST（JSON）。進捗は SSE（`text/event-stream`）でプッシュ。
  - バックエンド → 外部サイト: Selenium（ブラウザ操作）+ requests（画像 DL・収藏 POST）。
- **デプロイ方式**: Docker Compose による単一ホストマルチコンテナ。

### 2.2 リクエスト経路（重要）

フロントエンドは Next.js の **`rewrites()` でリバースプロキシ**として機能する。ブラウザは常に**フロントエンドのオリジン**（`:13000`）に `/api/*` を送り、Next.js が `http://backend:8000/api/*` へ転送する。

```
ブラウザ
  │  fetch("/api/...")  ・ EventSource("/api/events")
  ▼
frontend:3000 (Next.js)  ── rewrites: /api/:path* → http://backend:8000/api/:path*
  ▼
backend:8000 (FastAPI)
  ▼
db:5432 (PostgreSQL)
```

根拠: [frontend/next.config.mjs:11](../frontend/next.config.mjs#L11)、API クライアントの `API_BASE_URL = ""`（[lib/api/client.ts:2](../frontend/lib/api/client.ts#L2)）。
※ Komga（`:25601`）のみブラウザから直接アクセス（プロキシ経由しない）。

### 2.3 方式上の主要設計判断

| # | 設計判断 | 理由 / 効果 |
|---|---------|------------|
| 1 | 同期処理はシングルトン、DL 処理はキュー | 同期は重複実行で不整合を招くため排他。DL は要求を失わずに完遂させたいためキュー化。 |
| 2 | 長時間処理は `BackgroundTasks` + `tasks` テーブル + SSE | HTTP リクエストを即時に返し、進捗は非同期にプッシュ。リロード耐性のため状態を DB 永続化。 |
| 3 | クロールはジェネレータでストリーム処理 | お気に入りを 1 件ずつ即保存し、リアルタイム性と中断耐性を確保。 |
| 4 | 画像 DL・原図取得はスレッドプール並行 | I/O 待ちを並行化して高速化（既定 5 / 3 スレッド）。 |
| 5 | DL 先と Komga ライブラリを同一ボリューム共有 | コピー不要で即閲覧反映。 |
| 6 | 起動時に中断タスクを全 failed 化 | Docker 再起動でメモリ上の実行状態が失われるため、DB 上の宙吊りタスクを掃除。 |
| 7 | フロントは API 失敗時モックデータにフォールバック | 開発容易性（`mock-data.ts`）。 |

### 2.4 技術要素マッピング

| レイヤ | 技術 | 主モジュール |

| UI | Next.js 16 / React 19 / Tailwind / Radix | `app/`, `components/`, `features/` |

## 4. 機能設計（処理フロー）

各機能の入出力・処理ステップ・分岐・例外を定義する。シーケンス図は [§10](#10-シーケンス図集) 参照。

### 4.1 収藏夹同期（FN-SYNC）

| 項目 | 内容 |
|------|------|
| 起動 | SC-01 の「同期」ボタン → `POST /api/sync` |
| 入力 | なし（資格情報は環境変数） |
| 出力 | `task_id`、以後 SSE で進捗、完了時 `added_count`/`updated_count` |
| 前提 | Selenium 利用可・ログイン成功 |

処理ステップ:
1. `sync_singleton.is_running()` を判定。実行中なら **HTTP 409**。
2. `tasks` に `task_type=sync, status=pending` を作成し、`BackgroundTasks` へ登録、即レスポンス。
3. （バックグラウンド）`sync_singleton.start_task()` で排他取得。失敗時タスク failed。
4. **ローカルファイル検証**（FN-VERIFY を内部呼出）。
5. ブラウザ初期化 → ドメイン解決 → ログイン。失敗時 failed。
6. 書架ページ取得 → 作者カテゴリ抽出。
7. カテゴリ毎にページ巡回し漫画を yield:
   - 既存(`manga_url` 一致): 必要時ページ数更新 → `updated_count++`。
   - 新規: `mangas` 追加 → 詳細クロールで補完 → `added_count++`。
   - 一意制約違反: `rollback` し更新扱い。
8. 進捗を逐次 `update_task`（SSE 配信）。
9. 完了で `status=completed, progress=100`。
10. `finally`: `crawler.close()`、`sync_singleton.finish_task()`。

例外/分岐:
- ログイン失敗 → failed「登录失败」。
- Selenium 未導入 → failed「Selenium 未安装」。
- 個別漫画の処理失敗 → ログ出力しスキップ（全体は継続）。

### 4.2 漫画ダウンロード（FN-DL）

| 項目 | 内容 |
|------|------|
| 起動 | カードの DL ボタン / 「下載全部」/ 最近更新の DL |
| 入力 | `manga_id`（または `manga_ids[]` / `update_id`） |
| 出力 | `task_id`、SSE 進捗、CBZ ファイル |

処理ステップ（投入）:
1. `download_queue_manager.add_to_queue(manga_id)`:
   - 漫画なし → None（404 へ）。
   - DL 済み → None（「已下载」）。
   - 既存 pending/running タスク → 既存を返す。
   - それ以外 → `download` タスク（pending）を作成。
2. タスクが pending なら `download_executor` を `BackgroundTasks` 起動。

処理ステップ（実行器 `download_executor`、シングルトン）:
1. 既に実行中なら return（多重起動防止）。
2. キューが空になるまでループ:
   - 次タスク取得 → `start_execution()` で排他 → `execute_download_task()` → `finish_execution()` → 0.5 秒 sleep。

処理ステップ（1 件 `execute_download_task`）:
1. タスク running。
2. DL 済みなら completed。
3. ログイン（失敗 failed）。
4. `download_status=downloading`。
5. 詳細クロール（メタデータ取得）。
6. 画像 URL 一覧クロール（取得不能 failed）。
7. 並行 DL（断点续传・カバー保存・進捗反映）。
8. CBZ 生成 + `ComicInfo.xml` 同梱。
9. 一時ディレクトリ削除。
10. `mangas` 更新 → タスク completed(100%)。

### 4.3 最近更新同期（FN-RU）

| 項目 | 内容 |
|------|------|
| 起動 | SC-02 の「同期」ボタン → `POST /api/sync-recent-updates` |
| 出力 | `task_id`、完了時 `added_count`/`deleted_count` |

処理ステップ:
1. シングルトン判定（実行中 409）。
2. `mangas` から作者一意リスト → `excluded_categories` を除外。
3. 作者毎に基準日（最新 `updated_at`、無ければ 2000-01-01）算出。
4. ログイン。
5. 作者毎に検索（作成日時降順）→ 基準日より新しい作品を収集（古い作品到達で打ち切り）。
6. `recent_updates` に upsert。
7. 基準日より古い当該作者レコードを削除。
8. 完了で集計反映。

### 4.4 最近更新からのダウンロード（FN-RU-DL）

1. `recent_updates` から対象取得（なし 404）。
2. `mangas` に `manga_url` で既存判定。
   - 既存 → その `id` を使用。
   - 未存在 → `mangas` に追加（`is_favorited=false`）。
3. `add_to_queue` → executor 起動。

### 4.5 サイト側お気に入り登録（FN-FAV）

1. `manga_id` で `mangas` 取得（なし 404）。既収藏なら即成功。
2. `FavoriteService`: ログイン → aid 抽出 → カテゴリ取得 → 作者マッチ → `save_fav` へ POST。
3. 成功で `is_favorited=true`。

### 4.6 ファイル検証（FN-VERIFY）/ 状態更新（FN-SCAN）

- **FN-VERIFY**（`/api/verify-files`）: DL 済みレコードの CBZ 実在確認。欠損は状態リセット。
- **FN-SCAN**（`/api/update-download-status`）: `downloads/` 走査 → サニタイズ突合 → 新規 DL 済み判定・パス更新・欠損リセット。

### 4.7 漫画削除（FN-DEL）/ 一括削除

- 単体: `DELETE /api/manga/{id}` → CBZ・カバー物理削除 → レコード削除。フロントは状態から除去。
- 一括: フロントが選択 ID を `Promise.all` で個別 DELETE（`confirm` 確認後）。

### 4.8 タスク状態取得・SSE（FN-TASK）

- 状態取得: `/api/tasks/{id}`、`/api/tasks/running/list` 等。
- SSE: `/api/events` を購読し `task_created`/`task_updated` を受信。切断時フォールバックポーリング。

### 4.9 設定取得・更新（FN-CONFIG）

- `GET/PUT /api/settings`。URL は `http(s)://` 検証。空文字は null 化。

## 5. 非同期・バッチ処理設計

### 5.1 タスクライフサイクル

```
[作成] pending ──(executor/service が拾う)──▶ running ──▶ completed
                                                  │
                                                  └──▶ failed
[起動時] pending/running を一括 ──▶ failed（cleanup_stale_tasks）
```

- 状態は `tasks` テーブルで永続化。各遷移で SSE `task_updated` を配信。
- `progress`: 0–100。DL は「DL 比率 × 90%」+ パッケージ 10%。

### 5.2 排他制御の実装

| 機構 | クラス | 排他キー | 多重要求時 |
|------|--------|---------|-----------|
| 同期収藏 | `SyncSingleton`（プロセス内シングルトン + `Lock`） | `_running_task_id` | 409 |
| 同期最近更新 | `RecentUpdatesSingleton` | `_running_task_id` | 409 |
| DL 実行器 | `DownloadQueueManager`（`Lock` + `_is_executing`） | `_current_task_id` | キュー投入（拒否しない） |

> 注: シングルトンは**プロセスローカル**。バックエンドを複数プロセス/レプリカで動かす場合は排他が効かない（現構成は単一プロセス前提）。

### 5.3 キュー処理設計（DL）

- キュー実体は `tasks` テーブル（`task_type=download, status=pending`、`created_at` 昇順）。
- 実行器はメモリ上のフラグで「1 実行」を保証し、DB をキューストアとして用いる。
- 投入 API は executor を起動するが、既に走っていれば即 return（冪等）。

### 5.4 起動時初期化（`init_on_startup`）

1. Alembic マイグレーション自動適用（`run_migrations`）。
2. `cleanup_stale_tasks(cleanup_all_on_startup=True)` で中断タスク掃除。
- `lifespan` と `on_event("startup")` の両方に登録（フォールバック）。

## 7. データベース物理設計

論理定義は [データモデル.md](./データモデル.md)。物理面の補足:

| 項目 | 設計 |
|------|------|
| DBMS | PostgreSQL 15（Alpine） |
| 接続プール | SQLAlchemy `pool_size=10, max_overflow=20, pool_pre_ping=True`（[database.py:7](../backend/app/database.py#L7)） |
| 主キー | アプリ側 UUID 文字列（`uuid4`）。`app_config` のみ固定 `"singleton"`。 |
| マイグレーション | Alembic を起動時自動適用。無効リビジョン自己修復・空 DB 時初期生成・既存 DB 時 stamp。 |
| トランザクション | `autocommit=False, autoflush=False`。各操作で明示 `commit`/`rollback`。 |
| 文字コード | UTF-8（多言語タイトル対応） |
| 永続化 | `postgres_data` Docker ボリューム |

並行登録時の一意制約（`manga_url`）違反は捕捉して `rollback` し、既存レコード再取得または更新扱いで吸収する設計。

## 8. 共通設計

### 8.1 エラーハンドリング方針

| レイヤ | 方針 |
|--------|------|
| API（routers） | `HTTPException`（404/409/400/500）で返却。 |
| サービス | 例外捕捉しタスクを `failed`（`error_message` 設定）。`finally` で排他解放・`db.close()`・`crawler.close()`。 |
| クローラ | 要素単位で try/except、stale element 対策（リンク先読みキャッシュ）、フォールバックセレクタ。 |
| フロント | `ApiResponse{success,error}` 形式。失敗時トースト通知。SSE 切断時ポーリング。API 全滅時モックデータ。 |

`get_error_message()` で例外メッセージの 1 行目のみ抽出し、ログ肥大を抑制。

### 8.2 ロギング設計（loguru、[utils/logger.py](../backend/app/utils/logger.py)）

| 出力先 | レベル | ローテーション | 保持 | 圧縮 |
|--------|--------|--------------|------|------|
| コンソール（カラー） | DEBUG | — | — | — |
| `manga_YYYY-MM-DD.log` | DEBUG | 毎日 0 時 | 30 日 | zip |
| `error_YYYY-MM-DD.log` | ERROR 以上（+例外） | 毎日 0 時 | 90 日 | zip |
| `crawler_YYYY-MM-DD.log` | INFO（`name` に `crawler` 含む） | 毎日 0 時 | 15 日 | zip |

### 8.3 セキュリティ設計（現状）

- アプリ認証なし（単一ユーザー前提）。CORS 全許可。
- 資格情報は環境変数（`MANGA_USERNAME`/`MANGA_PASSWORD`）。未設定なら起動時例外で停止。
- 公開ネットワーク直結を想定しない（要 §11 留意・要件定義書）。

### 8.4 設定優先順位

1. `app_config.manual_manga_site_url`（DB、UI から設定）
2. 発布ページからの自動解決（`PUBLISH_PAGE_URL`）

### 8.5 命名・ファイル規約

- CBZ: `downloads/<safe_author>/<safe_title>.cbz`
- カバー: `covers/<safe_title>_cover.<ext>`
- サニタイズ: タイトル＝英数 + ` -_`、作者＝英数 + ` -_（）()`、空白→`_`、空作者→`未知作者`。

## 9. CRUD マトリクス

機能 × テーブルの操作（C=作成 R=参照 U=更新 D=削除）:

  │           │            │ create task(pending)──────────────────▶│      │
  │           │◀───────────│ {task_id}  │              │            │      │

### 10.3 最近更新からの DL

```
Front ── POST /download-from-update/{update_id} ──▶ Back
  Back: recent_updates 取得 (なし→404)
        mangas 既存判定
          ├ 既存 → manga_id 採用
          └ 未存在 → mangas 追加(is_favorited=false) → manga_id
        add_to_queue → executor 起動
  Back ──▶ {task_id}  （以降は 10.2 と同じ）
```

### 10.4 SSE 接続・フォールバック

```
Front(EventSource)              Back(/api/events)
  │── connect ──────────────────▶│ add_connection
  │◀── event: connected ─────────│
  │◀── event: task_updated ──────│ (broadcast 時)
  │        … 30 秒無通信 …        │
  │◀── ": heartbeat" ────────────│
  │   (切断検知 onerror)          │
  │   setInterval(fetchTask,10s)  │  ← フォールバックポーリング
  │   (再接続で connected → ポーリング停止)
```

### 10.5 起動シーケンス

```
uvicorn 起動
  │ lifespan / startup_event
  ├ run_migrations()         … Alembic 自動適用（自己修復含む）
  └ cleanup_stale_tasks()    … pending/running を全 failed 化
  → アプリ稼働
```
